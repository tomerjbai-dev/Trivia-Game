# ARCHITECTURE – חכמולוגים

> תאריך מחקר: 25 באוקטובר 2026  
> מסמך מקור: `PRD.md`  
> עיקרון מנחה: מערכת Web קטנה עם Backend מאובטח ל-AI, ללא Database וללא Authentication.

## 1. Technology Stack שנבחר

| רכיב | בחירה | תפקיד |
|---|---|---|
| Frontend | React + Next.js App Router + TypeScript | שלושה מסכים, אינטראקציות ו-RTL |
| עיצוב | CSS Modules + CSS רגיל | Responsive Mobile-first ללא תלות בספריית UI |
| Backend | Next.js Route Handler ב-Node.js runtime | API מאובטח ליצירת שאלות וסינון תוכן |
| אימות נתונים | Zod | בדיקת בקשות ותשובות בזמן ריצה |
| AI | OpenAI Responses API, מודל `gpt-5` | יצירת שאלה אחת בעברית במבנה מוגדר |
| סינון תוכן | OpenAI Moderation API (`omni-moderation-latest`) + הנחיות בטיחות במודל | חסימת תוכן לא מתאים לפני ואחרי יצירה |
| PWA | Web App Manifest ואייקונים; Service Worker מינימלי רק אם נדרש להתקנה בדפדפני היעד | התקנה מהדפדפן, ללא תמיכת Offline |
| Hosting | Vercel | פריסת Frontend ו-Backend באותו פרויקט, HTTPS |
| ניהול גרסאות | Git + GitHub | מקור אמת לקוד ופריסה אוטומטית |
| בדיקות | Vitest + React Testing Library; Playwright לבדיקות זרימה | בדיקת התנהגות ומניעת רגרסיות |
| Database / Auth / Object Storage | **לא נדרשים** | אין חשבונות, שמירת התקדמות או תוכן דינמי מתמשך |

### החלטות ונימוקים

- **Next.js לעומת Vite+React או SvelteKit:** שלוש החלופות מתאימות ל-UI. נבחר Next.js בשל שילוב טבעי של React ו-API Routes באותו Repository, תיעוד PWA רשמי, אינטגרציה ישירה ל-Vercel וקהילת פיתוח גדולה. אין צורך ב-SSR דינמי; אפשר לרנדר את המסכים כ-Static UI, כאשר ה-API הוא Serverless.
- **Vercel לעומת Netlify או Cloudflare Workers:** שלושתן מספקות פריסה מ-Git; Vercel מפשטת במיוחד את פריסת Next.js עם Route Handlers ו-Preview deployments. GitHub Pages אינו מתאים לבדו משום שאסור לחשוף את מפתח OpenAI בדפדפן.
- **OpenAI לעומת Gemini API או Anthropic API:** שלושתן מסוגלות לייצר טריוויה. נבחר OpenAI בזכות Structured Outputs, Moderation API ייעודי ותיעוד TypeScript. המודל הוא `gpt-5` (החלטת המשתמש). זהו מודל "חושב", ולכן כדי לאזן בין זמן ההמתנה לאיכות השאלות הקריאה מוגדרת עם מאמץ חשיבה נמוך (`reasoning.effort: "low"`) ותשובה קצרה (ראו ADR-3). אין לשלוח פרמטרים שהמודל אינו תומך בהם (למשל `temperature`). בתחילת Milestone 2 יש לוודא שהמודל זמין בחשבון ותומך ב-Structured Outputs. מודל ה-AI מוגדר דרך משתנה הסביבה `OPENAI_MODEL` כדי לאפשר החלפה ללא שינוי בקוד.
- **CSS Modules לעומת Tailwind או ספריית רכיבים:** שלושה מסכים אינם מצדיקים שכבת עיצוב נוספת; CSS Modules נותן בידוד סגנונות ללא תלויות כבדות.
- **ללא Database:** שמירת היסטוריית השאלות בזיכרון הדפדפן במהלך השימוש הנוכחי בלבד; אין שמירת התקדמות מתמשכת. לכן Supabase, Migrations ופרויקטי Database נפרדים אינם רלוונטיים.
- **Zod:** גם Structured Outputs אינו תחליף לבדיקת קלט ופלט בשרת.

### סיכונים, עלויות ומגבלות

1. **תוכן לילדים:** Moderation חוסם תוכן פוגעני מובהק, אך אינו מסווג התאמה לגיל 6–9, וייתכן שהוא פחות מדויק בעברית. בהחלטת המשתמש אין בגרסה זו רשימת נושאים חסומים או סיווג גיל נוסף; הנחיות ה-AI מבקשות לכתוב כל שאלה בצורה מתאימה לילדים, והשרת יחסום פלט מסומן או סירוב. בהתאם ל-PRD לא מבוצע אימות עובדתי נוסף; לכן עדיין ייתכנו שאלות שגויות או מטעות.
2. **גישה אנונימית ללא הגבלת שימוש:** כל בקשה עולה כסף. בהחלטת המשתמש (מפתח API של חשבון לימודים) אין בגרסה זו Rate Limiting, תקרת תקציב או התראות. המשמעות: מי שיודע את כתובת האתר יכול לייצר שימוש בלתי מוגבל במפתח. זה מקובל לפרויקט לימודי; יש לשקול מחדש לפני פרסום רחב.
3. **Vercel Hobby:** מיועדת לשימוש אישי ולא מסחרי בלבד, ומתאימה לפרויקט לימודי. מוצר מסחרי מחייב תוכנית מתאימה. עלויות ותקרות שימוש עשויות להשתנות.
4. **Vercel Functions:** Serverless מתאים לבקשת AI קצרה. ערכים: Timeout של 30 שניות לקריאת OpenAI בשרת, `maxDuration` של 60 שניות ל-Route Handler, ו-Timeout של 40 שניות בצד הדפדפן. במקרה של Timeout מוחזרת שגיאה ידידותית; אין צורך ב-Background Jobs. יעד זמן תגובה: עד כ-10 שניות ברוב המקרים.
5. **PWA Online-only:** התקנה אינה הופכת את האפליקציה לזמינה Offline. בעת ניתוק יש להציג הודעה מתאימה כאשר המסך עדיין פתוח; פתיחה חדשה ללא רשת עשויה להציג את שגיאת הדפדפן. אין ליצור Cache שמאפשר לשחק ללא רשת.
6. **מחירי OpenAI:** תמחור תלוי במספר Tokens ובמודל; `gpt-5` יקר יותר ממודלים קטנים, וגם Tokens של חשיבה נספרים. המחיר העדכני מופיע במחירון OpenAI. Moderation API מפורסם כחינמי למשתמשי OpenAI API.
7. **מוצר לילדים ותנאי שימוש:** יש לבדוק את תנאי השימוש של OpenAI לגבי מוצרים המיועדים לילדים מתחת לגיל 13 לפני פרסום לילדים אמיתיים מחוץ להקשר הלימודי.

## 2. ארכיטקטורת המערכת

### 2.1 מבנה ורכיבים

```text
דפדפן / PWA (עברית, RTL)
  ├─ בית: שם, תמונה, "בואו נשחק!"
  ├─ טריוויה: נושא, טעינה, שאלה, בחירה, משוב
  └─ אודות: הסבר לילדים
           │ HTTPS POST /api/questions
           ▼
Next.js Route Handler על Vercel (Node.js)
  ├─ אימות בקשה וגבולות קלט
  ├─ סינון נושא באמצעות Moderation
  ├─ יצירת שאלה ב-OpenAI Responses API
  ├─ סינון תוכן הפלט
  └─ אימות מבנה השאלה והחזרת JSON
           │
           ▼
       OpenAI API
```

אין תקשורת ישירה בין הדפדפן ל-OpenAI; אין Database, Session Server או Object Storage.

### 2.2 חלוקה ל-Modules

- **App Shell / Navigation:** מבנה משותף, סרגל תחתון קבוע, כיווניות RTL, ניהול מעבר בין שלושת המסכים.
- **Home:** הצגת שם, תמונה סטטית וכפתור מעבר לטריוויה.
- **Trivia UI:** שדה נושא, כפתור יצירה, תצוגת שאלה ותשובות, נעילת תשובות לאחר בחירה, משוב ויצירה נוספת.
- **Trivia Session (Client memory):** נושא שהוקלד, נושא השאלה המוצגת, שאלה נוכחית, בחירה ותוצאתה, ורשימת שאלות שכבר הוצגו במהלך השימוש הנוכחי. אין שימוש ב-`localStorage` לשמירת התקדמות.
- **About:** הסבר סטטי לילדים.
- **Question API:** בדיקת קלט, קריאות AI, סינון, בדיקת מבנה ומיפוי שגיאות.
- **AI Adapter:** הגדרות מודל, Prompt בעברית, Schema מובנה וקריאות OpenAI; מופרד מלוגיקת ה-HTTP.
- **PWA Assets:** Manifest, אייקונים ותמונה סטטית מקומית למסך הבית.

### 2.3 Data Model ומצב אפליקציה

אין ישויות הנשמרות במסד נתונים. המבנים הבאים חיים בזיכרון בלבד:

| מבנה | שדות מרכזיים | מיקום |
|---|---|---|
| `TriviaQuestion` | `id` (מקומי), `topic`, `question`, `options` (ארבע מחרוזות), `correctIndex` (0–3) | תגובת שרת / זיכרון Client |
| `TriviaSession` | `draftTopic`, `activeTopic`, `currentQuestion`, `selectedIndex` או `null`, `seenQuestions` (מחרוזות/מזהים בזיכרון), `status`, `errorCode` | React State |

- `seenQuestions` משמש להעברת דוגמאות מוגבלות של שאלות קודמות לשרת, כדי **לנסות** להימנע מחזרות. יש לשלוח לכל היותר 10 נוסחי שאלות אחרונות, באורך מוגבל; אין הבטחה למניעת כפילויות מלאה. גם שאלות שדולגו בלי מענה נכללות ברשימה.
- `id` נוצר מקומית להצגה ולניהול React State; אינו מזהה משתמש.
- תשובה נכונה מוחזרת ל-Client כחלק מהשאלה כדי לאפשר משוב מקומי מיידי; זה משחק לימודי, לא בחינה מאובטחת.
- מעבר מסך **שומר** את מצב המשחק (נושא, שאלה, בחירה) כל עוד האפליקציה פתוחה; לכן `TriviaSession` מנוהל ברמת ה-Layout המשותף (React Context) ולא בתוך דף הטריוויה. רענון או סגירה מאפסים את מצב המשחק; אין שחזור.

### 2.4 API פנימי

**`POST /api/questions`** (ללא Authentication)

בקשת JSON:

```json
{
  "topic": "דינוזאורים",
  "recentQuestions": ["איזה דינוזאור היה בעל שלוש קרניים?"]
}
```

תשובת הצלחה `200`:

```json
{
  "question": "מה אכלו רוב הטריצרטופסים?",
  "options": ["צמחים", "דגים", "חרקים", "בשר בלבד"],
  "correctIndex": 0,
  "topic": "דינוזאורים"
}
```

שגיאות צפויות:

| HTTP | `code` | התנהגות UI |
|---|---|---|
| 400 | `INVALID_TOPIC` | בקשה להקליד נושא תקין |
| 422 | `UNSAFE_TOPIC` | בקשה ידידותית לבחור נושא אחר |
| 502 | `GENERATION_FAILED` | הודעה ידידותית ו-"נסו שוב" |
| 503 | `SERVICE_UNAVAILABLE` | הודעה ידידותית ו-"נסו שוב" |
| 504 | `GENERATION_TIMEOUT` | הודעה ידידותית ו-"נסו שוב" |
| 429 | `TEMPORARILY_BUSY` | הודעה ידידותית על עומס אצל ספק ה-AI ו-"נסו שוב" |
| — (דפדפן) | `NETWORK_ERROR` | אין חיבור לאינטרנט / הבקשה לא הגיעה לשרת: הודעה ייעודית ו-"נסו שוב" |
| — (דפדפן) | `CLIENT_TIMEOUT` | לא התקבלה תשובה תוך 40 שניות: אותה הודעה כמו `GENERATION_TIMEOUT` |

כל הודעות ה-UI בעברית, לפי טבלת הנוסחים ב-`DESIGN.md` (סעיף 1.4); `code` הוא מזהה פנימי. אין להציג הודעות SDK או פרטי ספק לילד. `INVALID_TOPIC` לא אמור להופיע בשימוש רגיל, כי הכפתור מושבת כשהתיבה ריקה; השרת בודק בכל זאת.

**בדיקת בקשה:** `Content-Type: application/json`, גוף בקשה קטן (למשל עד 8KB), נושא שאינו ריק לאחר Trim, עד 100 תווים, עד 10 שאלות קודמות שכל אחת עד 200 תווים. הנתונים מהדפדפן נחשבים בלתי מהימנים; אין להכניסם כהוראות מערכת.

**בדיקת תשובת AI:** באמצעות Structured Outputs ו-Zod: אובייקט יחיד עם `question` לא ריק, `options` מערך של ארבע מחרוזות לא ריקות וייחודיות, ו-`correctIndex` שלם בטווח 0–3. לא מתבצע אימות עובדתי או דירוג איכות נוסף. אם המבנה שגוי, יש להחזיר `GENERATION_FAILED` עם אפשרות לניסיון ידני חוזר; אין צורך במנגנון תיקון רב-שלבי.

**ערבוב תשובות:** מודלי שפה נוטים למקם את התשובה הנכונה באותו מקום. לכן השרת מערבב באקראיות את סדר ארבע התשובות (ומעדכן את `correctIndex`) לפני שהוא מחזיר אותן לדפדפן.

### 2.5 Data Flow

1. הילד מזין נושא ולוחץ על כפתור יצירת שאלה (או Enter). הכפתור מושבת כשהתיבה ריקה. שינוי שדה הנושא בלבד אינו שולח בקשה ואינו מחליף שאלה.
2. ה-Client מציג אנימציית טעינה קטנה וטקסט **"מכינים לך שאלה מעניינת..."**, ומונע שליחה כפולה במהלך בקשה פעילה. אם כבר מוצגת שאלה, היא נשארת על המסך במצב נעול ומעומעם עד שהבקשה מסתיימת.
3. ה-Client שולח `topic` ואת השאלות האחרונות בזיכרון ל-`POST /api/questions`.
4. השרת מאמת קלט, ואז מריץ **במקביל** Moderation לנושא ויצירת שאלה ב-OpenAI, כדי לקצר את זמן ההמתנה. אם הנושא מסומן, השאלה שנוצרה נזרקת ומוחזר `UNSAFE_TOPIC`.
5. ההנחיות ל-OpenAI: שאלה אחת בעברית לגילאי 6–9, בלשון רבים/ניטרלית, קצרה (עד כ-15 מילים, תשובות עד כ-4 מילים), ללא ניקוד, ללא תוכן מפחיד/מיני/אלים או מסוכן, עם ארבע אפשרויות ותשובה נכונה אחת; השאלות הקודמות משמשות להימנעות מחזרות ככל האפשר. הנושא מועבר כנתון בלבד, לא כהוראה.
6. השרת בודק את תוכן הפלט ב-Moderation, מאמת Schema, מערבב את סדר התשובות ומחזיר שאלה אחת. אם הסינון נכשל או אינו זמין, אין להציג את הפלט.
7. ה-Client מציג את השאלה ומאפשר בחירה אחת בלבד. בחירה נכונה מסומנת בירוק עם הודעה מעודדת; שגויה באדום, עם הדגשת התשובה הנכונה. התשובות ננעלות.
8. לחיצה נוספת על יצירת שאלה יוצרת בקשה חדשה לפי הערך הנוכחי של תיבת הנושא. השאלה הישנה מוחלפת רק כשהבקשה החדשה הצליחה; במקרה כשל השאלה הישנה (אם הייתה) נשארת מוצגת, מתחתיה מופיעה הודעת השגיאה עם "נסו שוב", והנושא נשמר. אפשר לבקש שאלה חדשה גם לפני שעונים על הנוכחית.

### 2.6 אבטחה ופרטיות

- **אין Authentication או Authorization של משתמשים**, בהתאם ל-PRD. ה-API ציבורי, ובהחלטת המשתמש אין בגרסה זו הגבלת קצב או תקרת הוצאה (ראו סיכון 2).
- `OPENAI_API_KEY` נשמר **בצד השרת בלבד** במשתני סביבה של Vercel; לעולם לא בשם `NEXT_PUBLIC_*`, בקוד מקור או ב-GitHub. בסביבת פיתוח הוא נמצא בקובץ `.env.local` שאינו נכלל ב-Git.
- יש להשתמש ב-HTTPS, להימנע מ-CORS פתוח שלא לצורך ולהגביל גודל בקשות.
- אין לשמור פרטים אישיים, היסטוריית נושאים או תוכן שאלות ב-Database או ב-Analytics. יש לצמצם לוגים כך שלא יכילו את הנושאים שהקלידו ילדים או את תשובות ה-AI; לוגים תפעוליים יתמקדו בקודי שגיאה, זמן תגובה ושימוש מצטבר.
- קריאות OpenAI יישלחו עם `store: false` כאשר האפשרות נתמכת. הדבר אינו מבטל בהכרח לוגי Abuse Monitoring של הספק; יש לבדוק את מדיניות שמירת הנתונים ואת תנאי השימוש לפני השקה לילדים.
- Prompt Injection: יש להתייחס לנושא כנתון בלבד, לא כהוראות; הנחיות הבטיחות וה-Schema מוגדרים בצד השרת. Moderation אינו מבטיח חסימה מושלמת.
- מותר להשתמש באותו מפתח OpenAI בפיתוח המקומי ובאתר החי (מפתח של חשבון לימודים). המפתח נשמר רק ב-`.env.local` המקומי ובמשתני הסביבה של Vercel.

### 2.7 PWA, נגישות והתאמה למכשירים

### 2.8 GitHub, סביבות ו-Deployment

- **Repository אחד ב-GitHub** (`tomerjbai-dev/Trivia-Game`). עובדים ישירות על ענף `main`, בלי ענפי Feature ובלי Pull Requests, ובלי מערכת CI נפרדת. `package-lock.json` יישמר לנעילת תלויות. סודות וקובצי `.env*` מקומיים מוחרגים מ-Git, למעט `.env.example` ללא ערכים סודיים.
- **לפני כל push** מריצים מקומית typecheck, lint, בדיקות אוטומטיות ו-build. push מתבצע רק אם כולם עוברים.
- **Vercel Project אחד** המחובר ל-GitHub (מ-Milestone 5): כל push ל-`main` מעדכן אוטומטית את האתר החי. כלומר, אחרי Milestone 5 "דחיפה לגיטהאב" היא גם פרסום לכל המשתמשים.

- סביבת פיתוח מקומית (`npm run dev`) קוראת את אותם משתנים מתוך `.env.local`.
- בדיקות אוטומטיות (Unit, Component ו-E2E עם Playwright) רצות מקומית ומחליפות את קריאות ה-AI בתחליף מדומה (Mock) **בתוך קוד הבדיקה בלבד**, כדי לא לצרוך כסף ולקבל תוצאות יציבות. אין "מצב הדמיה" באפליקציה עצמה; בדיקות ידניות של האפליקציה משתמשות ב-AI האמיתי.
- פריסה אוטומטית לא דורשת הפעלת פקודת Deploy ידנית. במקרה תקלה ניתן לבצע Rollback ב-Vercel.
- אין Database ולכן אין Migrations, אין Supabase ואין צורך בשני פרויקטי Supabase.

### 2.9 החלטות תפעוליות נוספות

## החלטות מרכזיות (ADRs)

### ADR-1: כתובת נפרדת לכל מסך ומצב משחק ב-Context משותף
**הקשר:** לאפליקציה שלושה מסכים, ומצב המשחק (נושא, שאלה, בחירה) צריך להישמר במעבר ביניהם עד לרענון הדף.
**החלטה:** כל מסך הוא כתובת ב-App Router: `/` (בית), `/trivia` (טריוויה), `/about` (אודות). המעבר נעשה ב-`next/link`, ו-`TriviaSessionProvider` (React Context) עוטף את כל המסכים ב-Layout הראשי.
**השלכות:** ניווט בצד הלקוח שומר את המצב; רענון מאפס אותו כנדרש; כפתור "חזור" בדפדפן עובד באופן טבעי; כל המסכים נבנים כדפים סטטיים.

### ADR-2: הקמה ידנית של הפרויקט וגרסאות כלים
**הקשר:** `create-next-app` אינו פועל בתיקייה שכבר מכילה קבצים (`spec/`, `CLAUDE.md`, `.gitignore`). בנוסף, TypeScript 7 ו-ESLint 10 עדיין אינם נתמכים רשמית על ידי `typescript-eslint` ותוספי ה-ESLint של Next.js.
**החלטה:** `package.json` וקובצי התצורה נכתבו ידנית; נבחרו TypeScript ‏6.0 ו-ESLint ‏9 (Next.js ‏16, React ‏19). קובץ התצורה של Vitest הוא `vitest.config.mts`.
**השלכות:** התקנה נקייה ללא התנגשויות תלויות. כשהכלים יתמכו בגרסאות החדשות, אפשר לשדרג.

### ADR-3: מאמץ חשיבה נמוך במקום מינימלי
**הקשר:** בבדיקה מול OpenAI עם `reasoning.effort: "minimal"` השאלות הגיעו תוך כ-1–1.5 שניות, אבל חלקן היו שגויות או חסרות היגיון.
**החלטה:** (החלטת המשתמש) הקריאה ל-`gpt-5` נשלחת עם `reasoning.effort: "low"`. רמת הקושי של השאלות נשארת קלה-בינונית כמו ב-PRD.
**השלכות:** השאלות שנבדקו היו נכונות וברורות. זמן ההמתנה עלה לכ-5–9 שניות, עדיין בתוך היעד של עד כ-10 שניות. עלות כל שאלה עולה מעט, כי גם Tokens של חשיבה נספרים.

### ADR-4: בלי ניסיונות חוזרים של ה-SDK ו-Timeout קצר לסינון
**הקשר:** ה-SDK של OpenAI מבצע כברירת מחדל ניסיונות חוזרים אוטומטיים, שכל אחד מהם עולה כסף ומאריך את ההמתנה. בנוסף, כל הבקשה בשרת (יצירה + בדיקת הפלט) צריכה להסתיים לפני ה-Timeout של 40 שניות בדפדפן.
**החלטה:** לקוח OpenAI נוצר עם `maxRetries: 0`. ליצירת השאלה Timeout של 30 שניות, ולכל בדיקת Moderation Timeout של 5 שניות. בדיקת הנושא רצה במקביל ליצירה, ובדיקת הפלט אחריה, כך שהבקשה מסתיימת תוך כ-35 שניות לכל היותר. פלט שסומן בסינון מוחזר כ-`GENERATION_FAILED` (הילד רואה "אופס..." עם "נסו שוב"), ונושא שסומן כ-`UNSAFE_TOPIC`, בלי כפתור "נסו שוב".
**השלכות:** אין חיובים נסתרים מניסיונות חוזרים; התאוששות מתקלה נעשית רק בלחיצה על "נסו שוב". תקלה רגעית בשירות מוצגת לילד מיד במקום להיפתר אוטומטית.
